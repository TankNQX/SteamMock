## Top Issues

1. **Unsafe callback registry lifetime and re-entrancy in `src/synth.cpp`.**  
   The registry stores raw `void*` to game callback objects with no ownership model. `deliver_one` copies a pointer while holding `registry_mutex` and then invokes it after the lock is released, so the object can be freed in between. `wanted_size` performs a virtual call into game code while still holding the registry mutex, inviting re-entrant stub calls and deadlocks. Failures during registration/unregistration are swallowed, leaving the game silently without callbacks.

2. **TCP transport races and connection desync in `src/transport_tcp.cpp` / `src/socket_io.hpp`.**  
   `_socket` is read unsynchronized against `close()`, `connect()`, and the destructor. Framing/send failures in `exchange()` return `false` without closing the socket, so the next exchange operates on a desynchronized stream. `SO_RCVTIMEO`/`SO_SNDTIMEO` do not bound blocking `connect()` on Windows, `EINTR`/`WSAEINTR` is treated as a hard failure, and `ensure_winsock_started()` logs WSAStartup failure but still returns success.

3. **Server transcript corruption and unbounded runtime state in `src/server.cpp`.**  
   A short `std::fwrite` leaves the unwritten remainder of a transcript line in limbo, causing the next record to be appended after partial bytes and corrupting line framing. `_records` is appended forever, `_sessions` is never pruned, and `records()`/`records_since()` deep-copy large vectors including embedded JSON. The listener socket/handle is published before the owning thread is created, so a thread-construction failure leaks the handle.

4. **The client bridge serializes all calls behind one process-wide mutex during blocking I/O in `src/client.cpp`.**  
   `call()` holds `_mutex` across `connect()` plus `exchange()`, whose timeout can be up to 600000 ms. One stalled backend therefore blocks every other bridge call. Separately, `_configured` is set before `_host`, `_port`, `_timeout_ms`, and transport timeout are assigned, so an allocation failure during configuration leaves callers believing the client is usable.

5. **IDL/interface input is insufficiently validated and can emit invalid or semantically wrong generated code in `src/idl.cpp` and `src/interfaces.cpp`.**  
   Wrong-typed JSON members are silently accepted, call names are emitted raw as C++ identifiers and string literals with no escaping/identifier validation, multiple cstring parameters silently overwrite the version, version sanitization can collide (`"1.0"` and `"1_0"`), and a `[name, "bytes"]` row without a length emits invalid C++ (`steammock::Bytes{name, }`). Hooked-call fallback modes can also omit the required `bridge/synth.hpp` include.

6. **Untrusted numeric and type coercions cross signed/unsigned boundaries in `src/session.cpp`, `src/interfaces.cpp`, and `src/protocol.cpp`.**  
   JSON unsigned integers at or above 2^63 and negative values flow through signed conversions with implementation-defined or wrapping behavior. Several `as_int64` values are narrowed to `int`/`int32` without range checks. `protocol.cpp` treats a non-object `out` member identically to an absent one and silently omits it, hiding upstream serialization errors. A missing `iAchievement` becomes index 0 instead of an error.

7. **Signal, startup, and teardown lifecycle hazards in `src/backend_main.cpp`, `src/dllmain.cpp`, and `src/log.cpp`.**  
   Signal handlers are installed only after `server.start()`, so a SIGINT/SIGTERM during startup terminates abruptly and bypasses transcript flush/summary. The `std::atomic<bool>` signal flag is assumed lock-free but is not guaranteed to be. A function-local `thread_local std::string` in `dllmain.cpp` leaves a per-thread destructor registered after `FreeLibrary`, and `log_configure` can race with `log_enabled`/`log_write` because two separate acquire loads are used.

8. **Steam lobby API behavior is incorrect in `src/lobby.cpp`.**  
   The mock ticket decodes to 13 bytes but `kMockTicketBytes` is 14, so `pcbTicket` reports one extra byte. `SetLobbyData`/`SetLobbyMemberData` mutate metadata without emitting `LobbyDataUpdate_t`, leaving peers with stale data. The `kGameServerInit` side effect is not listed in `handled_calls()`, so the documented handled surface is wrong.

### `src/backend_main.cpp`

#### Signal handler assumes a lock-free atomic bool

`src/backend_main.cpp:42` · 🟠 **medium** · bug

A signal handler that stores to std::atomic&lt;bool&gt; is only async-signal-safe when the atomic is lock-free (C++ [support.runtime]p10). lock-free-ness of std::atomic&lt;bool&gt; is not guaranteed by the standard; it happens to hold on current mainstream targets but is an unverified assumption for correctness of Ctrl+C handling. Prefer the portable `volatile std::sig_atomic_t` flag, or at minimum assert the assumption.

<details>
<summary><b>Suggested change</b></summary>

```diff
-extern "C" void steammock_on_interrupt(int) { g_interrupted.store(true); }
+namespace {
+volatile std::sig_atomic_t g_interrupted{0};
+}
+
+extern "C" void steammock_on_interrupt(int) { g_interrupted = 1; }
```

</details>

#### Option values accepted even when they start with a dash

`src/backend_main.cpp:124-134` · 🟡 **low** · maintainability

take_value consumes the next token as the option value without checking whether it starts with '-', so `steammock --host --port 80` silently assigns host = "--port" and then reports the bare `80` as an unknown option, which is confusing. Reject a following token that begins with '-' (unless the value legitimately needs to) so typos surface as clear errors rather than corrupted values.

#### Boolean flags silently swallow an attached value

`src/backend_main.cpp:144-151` · 🟡 **low** · bug

Because the '=' splitting happens for every argument before the flag checks, `--list-api=yes` / `--show-profiles=no` (and `--help=x`, `--version=x`) are silently accepted with the value ignored, so a typo such as `--list-api=yes` does not do what the user asked and gives no feedback. Boolean flags should reject an attached value (has_value == true) with an error instead of ignoring it.

#### Signal handlers installed after startup

`src/backend_main.cpp:289-292` · 🟡 **low** · bug

The handlers are installed only after server.start() and the 'listening on' notice. A SIGINT/SIGTERM arriving during startup (scenario load or server.start()) uses the default disposition and terminates the process abruptly, bypassing server.stop() and the transcript flush/summary this shutdown path exists to guarantee. Install the handlers at the beginning of serve() (or main) and reset g_interrupted before starting, so the clean-shutdown invariant covers the whole lifetime.

#### Conflicting informational flags are silently resolved

`src/backend_main.cpp:317-322` · 🟡 **low** · maintainability

--list-api and --show-profiles are exclusive informational modes, but when both are supplied, --list-api silently wins and the user's --show-profiles intent is dropped. Consider detecting the combination in parse_args and reporting a conflict error, so contradictory invocations fail loudly instead of masking intent.

#### Truncated executable path goes undetected

`src/client.cpp:37-43` · 🟠 **medium** · bug

GetModuleFileNameA returns the buffer size (nSize), not zero, when the buffer is too small (and sets ERROR_INSUFFICIENT_BUFFER), so a path longer than MAX_PATH is silently truncated and then used for log_configure and _exe_name. The zero check only catches outright failure. Detect truncation via `length >= sizeof(buffer)` (or retry with a larger buffer) and construct the string from the returned length.

<details>
<summary><b>Suggested change</b></summary>

```diff

     char buffer[MAX_PATH] = {};
-    if (GetModuleFileNameA(nullptr, buffer, sizeof(buffer)) == 0) {
+    const DWORD length = GetModuleFileNameA(nullptr, buffer, sizeof(buffer));
+    if (length == 0 || length >= sizeof(buffer)) {
         return std::string();
     }
-    return std::string(buffer);
+    return std::string(buffer, length);
 }
```

</details>

#### Configured flag set before configuration completes

`src/client.cpp:77-80` · 🟠 **medium** · bug

_configured is set to true before _host/_port/_timeout_ms and _transport-&gt;set_timeout_ms have been assigned. If one of the subsequent allocations (std::string from the environment, std::to_string, log_write's concatenation) throws, call() catches it and returns false, but every later call short-circuits inside configure() and ensure_connected() then runs with empty host / port 0 / unset timeout. Move the flag assignment to the end of each successful path (or reset it on exception) so a failed first configure is retried instead of caching half-populated state.

#### Process-wide mutex held across blocking input and output

`src/client.cpp:163` · 🟠 **medium** · performance

call() holds the process-wide _mutex for the entire blocking round trip — connect() plus exchange(), whose wait can be up to STEAMMOCK_TIMEOUT_MS (max 600000 ms). One game thread parked on a stalled/unreachable backend therefore serializes every other bridge call behind the same lock for up to ten minutes. Consider not holding _mutex during socket I/O (pair replies by _sequence, with connect guarded separately) or otherwise reducing the serialized wait, so a single hung backend cannot freeze the whole game.

#### Quadratic event draining from a vector queue

`src/client.cpp:250-251` · 🟡 **low** · performance

_events is a std::vector, so erase(_events.begin()) shifts every remaining Json left; when many events are queued each take_event() is O(n) and draining is O(n²). Since this is a FIFO queue, use std::deque&lt;Json&gt; (O(1) pop_front) or keep a head index to avoid the repeated shifts.

#### Generated outputs written in place and non-atomically

`src/codegen_main.cpp:63-65` · 🟠 **medium** · bug

`src/codegen_main.cpp:204-210` · 🟠 **medium** · bug

#### thread_local destructor survives FreeLibrary

`src/dllmain.cpp:50-52` · 🔴 **high** · bug

A function-local `static thread_local std::string` has a non-trivial destructor, so the CRT registers a per-thread TLS destructor for it in this module. If the DLL is unloaded (`FreeLibrary`) while a thread that has called this export is still alive, that registered destructor points into unmapped module code and the process can crash when the thread later exits. `DisableThreadLibraryCalls` only suppresses DLL_THREAD_ATTACH/DETACH notifications; it does not unregister TLS destructors. Since the returned pointer only needs to be stable until the next call on the same thread, use trivially-destructible storage instead of a `thread_local` object with a destructor.

<details>
<summary><b>Suggested change</b></summary>

```diff
-    static thread_local std::string last;
-    last = client.session_id();
-    return last.c_str();
+    // One leaked string per thread keeps the pointer stable without a TLS
+    // destructor that could run after this module has been unloaded.
```

#### Allocation inside the exception filter expression

`src/synth.cpp:256-259` · 🔴 **high** · bug

This function is executed inside the `__except` filter expression while the fault is still in flight, but it allocates a `std::string` and calls `log_write` (which itself likely allocates and may take locks). Allocation or logging on the faulting thread during exception dispatch can fault again, deadlock on a lock the faulting thread already holds, or otherwise corrupt exception state and obscure the original crash. #### Use-after-free in callback delivery

`src/synth.cpp:370` · 🔴 **high** · bug

Use-after-free / TOCTOU: the registry stores raw `void*` to callback objects and the mutex only protects map access, not object lifetime. `deliver_one` copies the pointer while holding `registry_mutex`, then invokes it via `call_object_guarded(objects.front(), ...)` after the lock is released. If another thread runs `callback_unregistered`/`call_result_unregistered` and destroys the object between the copy and the call, this dereferences freed memory (the vtable read and the call both touch the freed object). Consider keeping the object alive through the call (e.g., have the registry own a ref-counted/shared ownership token, or dispatch under a scheme where unregister and delivery cannot race), rather than relying on raw pointers.

#### Virtual call into game code while holding the registry mutex

`src/synth.cpp:393` · 🔴 **high** · bug

`wanted_size(object)` is invoked while `registry_mutex` is held. `wanted_size` dereferences the callback object's vtable and performs a virtual call into game code (`size(object)`). If that game code re-enters the stub (e.g., registers/unregisters another callback or pumps callbacks), it will try to lock the same non-recursive `std::mutex` and deadlock. The object is guaranteed alive during its own `RegisterCallback` call, so compute `wanted_size(object)` before taking the lock and only log/insert under the lock.

#### Timeouts do not bound a blocking connect

`src/transport_tcp.cpp:107-111` · 🔴 **high** · bug

`SO_RCVTIMEO`/`SO_SNDTIMEO` only bound blocking `send()`/`recv()`; on Windows they do not limit the duration of a blocking `::connect()`, which is governed by the TCP stack's SYN retransmission timer (~21s by default). So the intended `_timeout_ms` (default 2000ms) is not enforced for connection attempts, and `connect()` can still stall far beyond the configured timeout, contradicting the transport's documented "never hangs forever" behavior. Use a non-blocking connect plus `select()`/`WSAPoll` on the writable event with `_timeout_ms` (then restore blocking mode), or pass an explicit timeout to `WSAConnect`.

#### Socket handle read unsynchronized against close and connect

`src/transport_tcp.cpp:131` · 🔴 **high** · bug

`_socket` is read here (and in `is_connected()`) without synchronization, while `close()`, `~TcpTransport()` and `connect()` can close and reassign the same handle from another thread. That is a data race and can lead to use-after-close or to `exchange()` operating on a recycled `SOCKET` value that the OS has handed to something else. `_timeout_ms` has the same problem with `set_timeout_ms()`. Guard `_socket` (and `_timeout_ms`) with a mutex held for the duration of `exchange()`, or explicitly document and enforce single-threaded use.

#### Framing failures leave the socket open

`src/transport_tcp.cpp:139-142` · 🟠 **medium** · bug

Several failure paths in `exchange()` return `false` without closing the socket, leaving partial or unread bytes that desynchronize the next framed exchange. Close the socket on any framing/send failure so a later call reconnects cleanly.

#### Transient recv interruptions treated as hard failures

`src/transport_tcp.cpp:31-34` · 🟡 **low** · bug

`recv()` returns `SOCKET_ERROR` (-1) for transient interruptions (`WSAEINTR`, or `EINTR` on POSIX builds), but `got <= 0` turns a spurious interruption into a hard exchange failure and abandons an otherwise healthy connection. Check `WSAGetLastError()`/`errno` and continue/retry on `WSAEINTR`/`EINTR`, failing only on genuine errors or graceful close (`got == 0`).
